# db2-json-store JSON indexing with SQL API

This page demonstrates JSON indexing features using the SQL API.

See also:
  * [README.md](../README.md)

## Create new security roles

As the SECADM user, 
```
CREATE ROLE add_payment_doc;
DB20000I  The SQL command completed successfully.

CREATE ROLE remove_payment_doc;
DB20000I  The SQL command completed successfully.

CREATE ROLE view_payment_doc;
DB20000I  The SQL command completed successfully.

GRANT ROLE add_payment_doc TO USER JEREMY;
DB20000I  The SQL command completed successfully.

GRANT ROLE view_payment_doc TO USER JEREMY;
DB20000I  The SQL command completed successfully.
```

## Add payment document type

As the admin user, add a new Payment document type:
```
CALL admin.add_document_type(2, 'Payment', 'VIEW_PAYMENT_DOC', 'ADD_PAYMENT_DOC', 'REMOVE_PAYMENT_DOC');

  Return Status = 0
```

## Create some sample data

As user JEREMY, use a ``db2 -td@`` shell to add 5000 payments:
```
BEGIN
  DECLARE v_bigint BIGINT;
  FOR r AS
    WITH t(i) AS (VALUES 1 UNION ALL SELECT i + 1 FROM t WHERE i < 5000) SELECT i FROM t
  DO
    CALL docuser.add_json_document(v_bigint, 2, NULL, NULL, '{"account_num" : ' || r.i || ', "encoded_data" : "' || REPEAT(HEX(HASH(r.i, 3)), 254) || '", "amount" : ' || r.i || '.49, "description" : "Monthly interest"}');
    SET v_bigint = NULL;
  END FOR;
END@
DB20000I  The SQL command completed successfully
```

> Note: Be patient! Running Db2 on a low-spec Chromebook for these tests, this step took 92 seconds.

Each JSON document generated by the above SQL is slightly too long to be represented by an inlined CLOB (the maximum inline length being 32000). Consequently the documents are stored in separate LOB space, and not compressed. This means that querying this unindexed data without an index is appreciably slow. For the purposes of testing, filesystem caching was disabled on the LOB tablespaces, thereby removing any buffering effect for repeated LOB fetches.

## Add an index

As admin user, add an index on the ``account_num`` property:
```
CALL admin.add_json_index('ACCOUNT_NUM', 2, '$.account_num', 'BIGINT', ?);

  Value of output parameters
  --------------------------
  Parameter Name  : P_INDEX_ID
  Parameter Value : 1

  Return Status = 0
```

## Create some more sample data

As user JEREMY, use a ``db2 -td@`` shell to add 4000 payments:
```
BEGIN
  DECLARE v_bigint BIGINT;
  FOR r AS
    WITH t(i) AS (VALUES 101 UNION ALL SELECT i + 1 FROM t WHERE i < 4100) SELECT i FROM t
  DO
    CALL docuser.add_json_document(v_bigint, 2, NULL, NULL, '{"account_num" : ' || r.i || ', "encoded_data" : "' || REPEAT(HEX(HASH(-r.i, 3)), 254) || '", "amount" : ' || -r.i || '.49, "description" : "Fee"}');
    SET v_bigint = NULL;
  END FOR;
END@
DB20000I  The SQL command completed successfully
```

Note that the index has not yet been fully built (and hence is not usable). It only contains entries for rows added after the index was added:
```
SELECT COUNT(*) AS index_entry_count FROM json_bigint_index_value;

INDEX_ENTRY_COUNT
-----------------
             4000

  1 record(s) selected.
```

## Build the index

Call the stored procedure for building indexes:
```
CALL index.build_index(2, 'ACCOUNT_NUM');

  Return Status = 0
```

The index is now fully built.


## Testing the index

We can compare retrieval speed with and without the index.

First we specify a query that uses the created index to search for qualifying documents:
```
SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(start_ts);

SELECT
  d.document_id,
  d.document_type_name,
  d.inserted_utc_ts
FROM
  TABLE(docuser.get_json_bigint_values(2, '$.account_num')) AS i
    CROSS JOIN
  TABLE(docuser.get_json_document(i.document_id)) AS d
WHERE
  i.value = 3123;

SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(end_ts);

START_TS               
-----------------------
2026-11-22-16.11.05.274

  1 record(s) selected.

DOCUMENT_ID          DOCUMENT_TYPE_NAME             INSERTED_UTC_TS    
-------------------- ------------------------------ -------------------
                8028 Payment                        2026-11-22-02.35.58
                3128 Payment                        2026-11-22-02.26.57

  2 record(s) selected.

END_TS                 
-----------------------
2026-11-22-16.11.05.638

  1 record(s) selected.

```

The index was defined with JSON path ``$.account_num``. In full this is could be written ``lax $.account_num``. By instead specifying ``strict $.account_num`` in the query, index use is disabled (done because the results _might_ not always be identical). The query will then parse the 9000 JSON documents to determine the results:
```
SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(start_ts);

SELECT
  d.document_id,
  d.document_type_name,
  d.inserted_utc_ts
FROM
  TABLE(docuser.get_json_bigint_values(2, 'strict $.account_num')) AS i
    CROSS JOIN
  TABLE(docuser.get_json_document(i.document_id)) AS d
WHERE
  i.value = 3123;

SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(end_ts);

START_TS               
-----------------------
2026-11-22-16.11.40.609

  1 record(s) selected.


DOCUMENT_ID          DOCUMENT_TYPE_NAME             INSERTED_UTC_TS    
-------------------- ------------------------------ -------------------
                3128 Payment                        2026-11-22-02.26.57
                8028 Payment                        2026-11-22-02.35.58

  2 record(s) selected.

END_TS                 
-----------------------
2026-11-22-16.11.44.763

  1 record(s) selected.
```

In the above example, the indexed query took less than 0.4 seconds, versus over 4 seconds for the equivalent unindexed query.

# db2-json-store JSON indexing with SQL API

This page demonstrates JSON indexing features using the SQL API. For a full list of supported search functions see [module_JINDEX.sql](../db2/schema_DOCSTORE/module_JINDEX.sql).

## Add payment document type

As the admin user, add a new Payment document type:
```
CALL admin.add_document_type(2, 'Payment', 'VIEW_PAYMENT_DOC', 'ADD_PAYMENT_DOC', 'REMOVE_PAYMENT_DOC', 'ADD_PAYMENT_DOC');

  Return Status = 0
```

## Create some sample data

As user JEREMY, use a ``db2 -td@`` shell to add 5000 payments:
```
BEGIN
  DECLARE v_bigint BIGINT;
  FOR r AS
    WITH t(i) AS (VALUES 1 UNION ALL SELECT i + 1 FROM t WHERE i < 5000) SELECT i FROM t
  DO
    CALL jdoc.add_document(v_bigint, 2, NULL, NULL, '{"account_num" : ' || r.i || ', "encoded_data" : "' || REPEAT(HEX(HASH(r.i, 3)), 254) || '", "amount" : ' || r.i || '.49, "description" : "Monthly interest"}');
    SET v_bigint = NULL;
  END FOR;
END@
DB20000I  The SQL command completed successfully
```

> Note: Be patient! Running Db2 on a low-spec Chromebook for these tests, this step took 82 seconds.

Each JSON document generated by the above SQL is slightly too long to be represented by an inlined CLOB (the maximum inline length being 32000). Consequently the documents are stored in separate LOB space, and not compressed. This means that querying this unindexed data without an index is noticeably slow. For these tests, filesystem caching was also disabled on the LOB tablespaces to remove any buffering of LOB reads.

## Add an index

As admin user, add an index on the ``account_num`` property:
```
CALL admin.add_index(2, 'ACCOUNT_NUM', '$.account_num', 'BIGINT', ?);

  Value of output parameters
  --------------------------
  Parameter Name  : P_INDEX_ID
  Parameter Value : 1

  Return Status = 0
```

## Create some more sample data

BEGIN

Note that the index has not yet been fully built. It only contains entries for rows added after the index was added. We can see this if we have permissions to query the table holding indexed entries:

## Build the index

Call the stored procedure for building indexes:
```
CALL indexer.build_index(2, 'ACCOUNT_NUM');

  Return Status = 0
```

It is expected that pending index builds will be automated e.g. by a scheduled script.

The index is now fully built:
```
SELECT
  index_id, index_name, CAST(json_path AS VARCHAR(30)) AS json_path, value_data_type, inserted_utc_ts, is_build_pending, is_delete_pending

## Testing the index

We can compare retrieval speed with and without the index.

First we specify a query that uses a table function search the index for documents with account number 3123:
```
SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(start_ts);

SELECT
  d.document_id,
  JSON_VALUE(d.json_document, '$.account_num' RETURNING BIGINT) AS account_num,
  d.document_type_name,
  d.inserted_utc_ts
FROM
  TABLE(jindex.get_bigint_values_eq(2, '$.account_num', 3123) CARDINALITY 5) AS i
    CROSS JOIN
  TABLE(jdoc.get_document(i.document_id)) AS d;

SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(end_ts);

START_TS               
-----------------------
2026-11-27-19.45.54.894

  1 record(s) selected.

DOCUMENT_ID          ACCOUNT_NUM          DOCUMENT_TYPE_NAME             INSERTED_UTC_TS    
-------------------- -------------------- ------------------------------ -------------------
                3127                 3123 Payment                        2026-11-27-05.54.05
                8027                 3123 Payment                        2026-11-27-05.57.20

  2 record(s) selected.

END_TS                 
-----------------------
2026-11-27-19.45.54.914

  1 record(s) selected.
```

> Note: By default the Db2 optimizer assumes 1000 rows returned from a compiled table function. This is likely too high in most cases, and currently our table currently contains only 9000 documents. So the CARDINAILITY clause is used to ensure the optimiser does not attempt a more costly scan of the documents table. In a large database this cause should be unnecessary.

The index was defined with JSON path ``$.account_num``. In full this is could be written ``lax $.account_num``. By instead specifying ``strict $.account_num`` in the query, index use is disabled, because the results _might_ not always be identical. Consequently, in this example the GET_BIGINT_VALUES_EQ table function falls back to parsing 9000 JSON documents on-the-fly (instead of using the pre-built index):
```
SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(start_ts);

SELECT
  d.document_id,
  JSON_VALUE(d.json_document, '$.account_num' RETURNING BIGINT) AS account_num,
  d.document_type_name,
  d.inserted_utc_ts
FROM
  TABLE(jindex.get_bigint_values_eq(2, 'strict $.account_num', 3123) CARDINALITY 5) AS i
    CROSS JOIN
  TABLE(jdoc.get_document(i.document_id)) AS d;

SELECT * FROM (VALUES CURRENT_TIMESTAMP(3)) AS t(end_ts);

START_TS               
-----------------------
2026-11-27-19.49.03.717

  1 record(s) selected.

DOCUMENT_ID          ACCOUNT_NUM          DOCUMENT_TYPE_NAME             INSERTED_UTC_TS    
-------------------- -------------------- ------------------------------ -------------------
                3127                 3123 Payment                        2026-11-27-05.54.05
                8027                 3123 Payment                        2026-11-27-05.57.20

  2 record(s) selected.

END_TS                 
-----------------------
2026-11-27-19.49.07.661

  1 record(s) selected.
```

In the above example, the indexed query took 0.02 seconds, versus almost 4 seconds for the equivalent unindexed query.

## Remove an index

As admin user, remove the index on the ``account_num`` property:
```
CALL admin.remove_index(2, 'ACCOUNT_NUM');

  Return Status = 0
```

The index is now flagged as pending deletion:
```
SELECT
  index_id, index_name, CAST(json_path AS VARCHAR(30)) AS json_path, value_data_type, inserted_utc_ts, is_build_pending, is_delete_pending
FROM
  TABLE(info.get_indexes(2));

INDEX_ID INDEX_NAME                     JSON_PATH                      VALUE_DATA_TYPE      INSERTED_UTC_TS     IS_BUILD_PENDING IS_DELETE_PENDING
-------- ------------------------------ ------------------------------ -------------------- ------------------- ---------------- -----------------
       1 ACCOUNT_NUM                    $.account_num                  BIGINT               2026-11-27-05.56.02                0                 1

  1 record(s) selected.
```

Call the stored procedure for purging indexes:
```
CALL indexer.purge_index(2, 'ACCOUNT_NUM');

  Return Status = 0
```

It is expected that pending index deletions will be automated e.g. by a scheduled script.

The index no longer exists:
```
